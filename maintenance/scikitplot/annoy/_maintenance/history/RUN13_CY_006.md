# Run 13 — CY-006 (guide Part II §29.3) — `set_params` metadata/type divergence

**Priority:** P1  **Area:** `annoy/_annoy/annoylib.pyx.in` (`Index.set_params`)  **Gate tier:** ring

## Finding (runtime-verified)
`f` and `metric` were immutable after construction, but the structural TYPE
parameters `index_dtype`, `dtype`, `wrapper_dtype`, `random_dtype` were set with a
bare `setattr`. `set_params(index_dtype='int64')` on a constructed index changed
the *reported* metadata to `int64` while the concrete pointer/enum dispatch stayed
`int32` — a metadata/type divergence. Unknown keys were also silently ignored.

Reproduced: `Index(4,'euclidean').set_params(index_dtype='int64')` returned
successfully and `get_params()['index_dtype']` became `int64` while operations
continued through the int32 backing.

## Fix (guide decision 1 — structural params immutable once constructed)
- The four structural type params now raise
  `ValueError("Cannot modify '<param>' after index construction …")` when
  `self.ptr != NULL`, exactly mirroring the existing `f`/`metric` guards. No
  silent metadata-only mutation.
- Unknown parameters are rejected: `_valid = get_params() keys ∪ handled keys`,
  and any key outside it raises `ValueError("Invalid parameter(s) …")`. Using the
  live `get_params()` keys keeps `set_params(**get_params())` round-trip-safe.
- `clone()` uses `__init__` (not `set_params`) — as the pre-existing `f`/`metric`
  immutability already relied on — so this does not break sklearn cloning. Diff:
  `out/annoylib.pyx.in.run13.diff`.

## Verification
`tests/test_set_params_immutable.py` (10 tests): each structural param
(`index_dtype`/`dtype`/`wrapper_dtype`/`random_dtype` + `metric`/`f`) raises after
construction; a rejected `index_dtype` change leaves the metadata unchanged (no
divergence); an unknown parameter raises; mutable params (`n_neighbors`, `seed`)
still work; and `set_params(**get_params())`'s mutable subset round-trips. Ring
green: annoy/_annoy 345, euclidean 12, types 8, kiss 123.

## Note
The guide also observed "zero values for positive params accepted" — a separate
pre-construction numeric-validation concern (distinct from the divergence defect),
left as a small follow-up rather than widened into this run.
