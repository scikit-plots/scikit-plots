# Run 16 — CY-010 (guide Part II §34) — typed state restore reconstructs wrong concrete type

**Priority:** P1  **Area:** `annoy/_annoy/annoylib.pyx.in` (`Index.set_state`)  **Gate tier:** ring

## Finding (runtime-verified)
Pickling/unpickling an index built with a non-default `index_dtype` (`int64`,
`uint64`) failed hard: `RuntimeError: Failed to deserialize index: Serialized
data is corrupt (n_nodes < n_items)`, and could abort the process. Default
`int32`, all metrics, and `dtype=float64` round-tripped fine; native `save`/`load`
of an int64 index also worked — so the native format and int64 backing are
sound. The defect was isolated to the pickle (`get_state`/`set_state`) path, and
`index_data` was present (not the §34.4 silent-drop case).

## Root cause
`_ensure_index()` dispatches the concrete native type on the ENUMS
`index_type_id` / `data_type_id`. `__init__` derives those enums from the dtype
strings via `parse_index_dtype()` / `parse_data_dtype()`. But `set_state`
restored only the dtype STRINGS (`self.index_dtype = ...`), never the enums —
which stayed at the reconstruction default (int32). So on unpickle,
`_ensure_index()` built an int32 backing and then tried to deserialize an int64
blob, whose node stride differs → `n_nodes < n_items`.

## Fix (minimal, mirrors __init__)
In `set_state`, after restoring the dtype strings, derive the dispatch enums the
same way `__init__` does:
`self.index_type_id = parse_index_dtype(self.index_dtype)` and
`self.data_type_id = parse_data_dtype(self.dtype)`. Now the reconstructed concrete
type matches the serialized blob. Diff: `out/annoylib.pyx.in.run16.diff`
(+~10 lines, one file).

## Verification
`tests/test_typed_state_roundtrip.py` (12): pickle round-trip preserves exact
type metadata + data across `index_dtype` ∈ {int32,int64,uint64}, all 5 metrics,
`dtype` ∈ {float32,float64}, the combined int64+float64 case, and query
(`get_nns_by_vector`) numerical semantics on a restored int64 index. Ring green:
annoy/_annoy 363, annoy serialize 3, euclidean 12, kiss 123.

## Note
`get_state` already emits `index_data` (no silent `None`), so §34.4's data-loss
policy is satisfied for these paths. Whether the *concrete backing* honours
`index_dtype` at construction (vs the R13/CY-006 metadata-only story) is a
separate specialization/honesty question (CY-013/CY-016); this run guarantees the
state path faithfully reconstructs whatever type was built.
