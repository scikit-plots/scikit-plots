# Run 21 — CY-019 (guide Part II §39) — docstring/default/type-count drift

**Priority:** P2  **Area:** `annoy/_annoy/annoylib.pyx.in` (`Index.__init__` docstring)  **Gate tier:** ring

## Finding (source-confirmed)
The `Index.__init__` docstring had drifted from the code in two confirmed places,
each contradicting the accurate class-level (`BaseIndex`) docstring:
- `index_dtype`: documented `default="int64"` while the real default is `"int32"`,
  and claimed *"Currently only int32, int64 supported. Future: uint8, uint32,
  uint64"* — but all eight integer types (`int8/uint8/int16/uint16/int32/uint32/
  int64/uint64`) construct AND build.
- `dtype`: claimed *"only float32, float64 supported. Future: ... float16,
  float128"* — but `float16`, `float32`, `float64`, `float128` all work today.

## Fix (documentation parity)
Rewrote both `Index.__init__` parameter entries to state the correct default
(`int32`) and the actual supported sets, pointing to the class docstring for the
per-type limits/precision notes (which were already correct). No behaviour change.
Diff: `out/annoylib.pyx.in.run21.diff`.

## Verification
`tests/test_doc_parity.py` (15) turns the docs into an enforced contract:
documented `index_dtype`/`dtype` defaults equal the real constructed defaults;
EVERY integer type (8) and float type (4) named in the docstring actually
constructs+builds; and the stale "Future"/"only int32,int64" claims are gone. This
locks doc↔code parity so it cannot silently drift again. Ring green: annoy/_annoy
409, euclidean 12, kiss 123.
