# Run 22 — CY-012 (guide Part II §39) — float128 public precision vs the double bridge

**Priority:** P2  **Area:** `annoy/_annoy/annoylib.pyx.in` (`add_item` precision contract)  **Gate tier:** ring

## Finding (numeric contract gap)
`dtype="float128"` is a supported type, but ALL embeddings flow through the
double-precision (`double*`) `_w` bridge (add_item_w/get_item_w). So `float128`
(and `float16`) I/O is capped at double precision — `float128` provides no extra
input/output precision, only higher-precision INTERNAL distance arithmetic.
Verified: for `1.0 + 2**-40`, `float128` and `float64` return byte-identical
values. The class docstring already carried the caveat, but the I/O-boundary
methods (`add_item`) — where the narrowing actually happens — did not.

## Fix (honest, consistent contract)
Added a precision note to `add_item`: embeddings are converted to `double` at the
bridge regardless of `dtype`; `float16` is narrowed, `float128` gains no input
precision (only internal-arithmetic precision), and users must not rely on
more-than-double input precision being preserved. The canonical per-type note
stays in the class docstring; the R21 `dtype` entry already cross-references it.
No behaviour change. Diff: `out/annoylib.pyx.in.run22.diff`.

## Verification
`tests/test_float128_precision_contract.py` (4): `float128` I/O is byte-identical
to `float64` I/O for the same input (double-cap locked); `float128` still
builds/queries correctly; `float16` narrows through the bridge without error; and
the precision contract is documented on both `add_item` and the class docstring.
Ring green: annoy/_annoy 424, kiss 123.

## Note
This is an honesty/labeling fix — `float128`'s internal-arithmetic benefit is
real and retained. Making the bridge itself wider than `double` would be a
substantial ABI/format change (out of scope, and overlaps the §6.6 format
decision).
