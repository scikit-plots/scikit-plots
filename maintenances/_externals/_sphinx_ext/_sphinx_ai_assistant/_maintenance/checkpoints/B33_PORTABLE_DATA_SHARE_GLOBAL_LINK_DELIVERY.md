# B33 — Portable Data Share and Global Link Delivery

Status: **COMPLETE — Run 16.2 quick sharing fix**

## Problem

Two user-facing delivery paths were not reliable enough:

1. current self-contained `#ai-share-c1` / `#ai-share-c2` hash links depended on the host documentation page/router and were not portable enough for the requested cross-device copy/send workflow;
2. a compatible Global Share backend could successfully return a public UUID without a URL, leaving the user without a shareable cloud link even though creation succeeded.

## Current contract

### Self-contained

Current generation is an exact bounded:

```text
data:text/html;charset=utf-8;base64,<reviewed-static-document>
```

The document is produced only from `_normalizeShareSnapshot()` output. It is static/inert: no executable script, forms, frames, workers, external network resources, or clickable external links. Base64 is **not encryption**; anyone with the data URL can decode the shared content. Copied URLs are not remotely revocable and can remain in clipboard/history/messages.

Legacy `c1`/`c2` parsing remains compatibility-only. `c1.html` stays inert text. `c2` stays schema-validated but is no longer generated by the current Self-contained action.

Browser policy caveat: top-level page-initiated `data:` navigation is not universally allowed. **Run 16.2.1 correction:** **Copy data link** and **Open** now use the same exact portable `data:text/html;charset=utf-8;base64,...` artifact; Open never substitutes `blob:`. If the browser blocks page-initiated data navigation, the UI reports that limitation and the recipient can explicitly open the same copied URL.

**Run 16.2.2 Global-link visibility correction:** `Create global link` now renders an inline operation state immediately (`Creating global link…`) and must terminate in either a visible validated public read URL or a visible bounded error with Retry. `_remotePost` no longer swallows empty/non-JSON 2xx responses, fetch/CORS rejection, serialization failure, or synchronous request-start failure. Arbitrary HTML/proxy response bodies are not reflected into the UI.

### Global

A successful Global Share operation must end with a validated public read URL visible to the user and stored in the managed artifact lifecycle. Preferred server response fields are `url` / `publicUrl` / `shareUrl` / `share_url`. If a compatible backend returns only a valid Share UUID, the client synthesizes only the configured fixed viewer form:

```text
https://<configured-share-host>/v1/share#share=<validated-id>
```

Invalid/missing locators fail closed. Managed Global artifacts expose **Copy link** in addition to Open/Check/Revoke/Forget as applicable.

## Security/privacy boundary

- reviewed normalized snapshot only;
- 256 KiB portable content ceiling + 384 KiB encoded URL ceiling;
- no active HTML execution primitive from user content;
- no external resource/network exfiltration in portable document;
- base64 never described as encrypted/private;
- copied self-contained links never described as remotely revocable;
- Global URL synthesis is anchored to the configured `/v1/share` endpoint and a validated UUID;
- Global edit/revoke capability remains separate and page-memory-only.

### Run 16.2.3 local-preview action consistency

Local preview now exposes the same inspectable action pattern as Self-contained without changing its trust boundary: **Copy link | Open | Inspect | Remove from browser**. The copied value is the existing browser-local `blob:` URL; it is not uploaded, not portable, and is valid only while that Blob URL remains alive in the current browser/session. Inspect reveals the exact Blob URL. Remove from browser revokes it. In **Created artifacts**, local and self-contained rows use the compact standard **Copy link | Open | Remove** pattern; Global retains its additional Check status / Revoke / Forget lifecycle actions because those represent real server state.



### Run 16.2.4 official-docs CORS deployment correction

Live browser evidence showed `Create global link` reaching the HF Share endpoint but receiving `HTTP 403 Origin not allowed` from the deployed proxy while the documentation page was served from the official `https://scikit-plots.github.io` origin. The runtime default already named that origin, so an `ALLOWED_ORIGINS` environment override could replace the default and accidentally disable the shipped UI. Run 16.2.4 changes `ALLOWED_ORIGINS` to **additive** semantics: the official Scikit-Plots documentation origin is a package-owned exact-origin trust anchor, additional configured exact origins are merged after strict HTTP(S)-origin validation, and only explicit `*` selects wildcard compatibility. HF and Worker implementations match. Proxy patch version is `6.5.1`, and `/health` exposes privacy-safe CORS diagnostics (`official_docs_origin_allowed`, wildcard flag, count, additive semantics) without publishing custom/private origin values.

## Run 16.2.7 lifecycle UI correction

After a successful Global revoke, the operation lock must be cleared before the
terminal `revoked` state is rendered. Otherwise the row correctly changes from
**Revoke** to **Forget** but the replacement action remains disabled. Forget is
local lifecycle cleanup only and never substitutes for server revocation.
